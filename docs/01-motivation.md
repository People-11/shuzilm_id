# 1. 动机

## 起因

我们在维护一个某社区的第三方客户端（个人使用，不公开分发）。某天下午，这个社区出于我们无从得知的原因，在短时间内让所有旧版本客户端的评论等请求全部失效。

以往这类限制只是提高版本号门槛，改一下请求里的版本号就能绕过。这一次不同：新版官方客户端引入了新一代请求令牌，并且要求请求携带由数字联盟 SDK 生成的设备 ID（`smid`）。单纯伪装成旧版本已经行不通，第三方客户端要继续可用，就得面对这两样东西。

于是我们开始重写这个客户端。令牌部分与本仓库无关，这里不展开。设备 ID 部分，我们本可以直接在第三方客户端里加载官方的 `libdu.so`，但这意味着在自己的客户端里运行一段完全不透明的闭源采集代码。我们更希望弄清楚它到底发送了什么，然后只发送必要的部分。所以我们决定逆向 `libdu.so`，用纯 Kotlin 自己实现一遍。

## 为什么变成了一次披露

实现“拿到一个 ID”所需的字段其实很少（[5.4](05-libdu-behavior.md#54-首次注册上报-mdna)，十几个）。但在逐字段还原 libdu 的上报时，我们发现它收集的东西远远超出了一个“设备标识”所需：

- Root、Magisk、Xposed / LSPosed、Frida、调试器检测；
- SELinux 状态、开发者选项、ADB、USB 调试；
- TLS 证书校验是否被 Hook、系统是否接受空证书链、用户装了哪些 CA 证书；
- hosts 文件的内容、启用了哪些无障碍服务；
- 局域网里其他设备的 MAC、周围的 Wi-Fi 和蓝牙设备；
- 其他公司 SDK 存下的设备 ID；
- 一个写在共享存储上、卸载后仍然留存、所有接入 SDK 的 App 都会读取的跨应用 ID。

这些数据和数盟官网“识别设备唯一 / 判断设备风险”的宣传放在一起看，意思就很清楚了：这不是一个单纯的设备号，而是一份跟着设备走、在所有接入了 SDK 的 App 之间共享的环境档案。

随着挖出来的东西越来越多，我们认为这件事不应该只停留在一个第三方客户端的代码注释里。集成了这个 SDK 的 App 数量很大，绝大多数用户并不知道它会发送什么。出于对用户隐私和社区环境的考虑，我们决定整理成文，有责任地公开。

## 这份材料想做到的

- **可核对**：每一条结论都标注 libdu 中的函数位置，附带样本哈希和工具，任何人都可以对照同一份二进制独立验证；
- **只陈述事实，推断单独标注**：客户端行为是事实，服务端怎样用这些数据是推断，两者分开写；
- **不帮倒忙**：不提供可以直接滥用的东西（客户密钥、批量伪造设备上报的工具、绕过宿主 App 安全机制的方法），详见 [2. 有责任的披露](02-responsible-disclosure.md)。
